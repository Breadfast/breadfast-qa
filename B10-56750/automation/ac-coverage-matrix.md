## Notes
1. **AC-03 seeded-data scope** — the Figma export (reused from B10-56729) shows four sections (Breadfast, General, Food & Beverage, Fitness); the LIVE environment at capture time had only **Breadfast** and **General Purchases** seeded. The test asserts against what is actually live, not the Figma list, and flags the "General Purchases" vs "General" resolution (see note 8).
2. **AC-05 AR-requiredness — RESOLVED.** Live: submitting with EN filled and AR empty renders "This field is required." under the AR field and blocks submission. This resolves requirements-analysis.md Risk 2 in favor of "AR is required," contradicting the AC text's implication that only EN is required.
3. **AC-08 toast** — the "Section created successfully" toast was observed live during manual capture but is timing-sensitive to automate reliably (a 4s poll is used, best-effort; a miss is annotated, not failed).
4. **AC-09/AC-10 wording deviations** — live confirmed: (a) the duplicate-name error is a single shared `<span class="text-danger">` below both fields, NOT a red border/aria-invalid highlight on the name field itself (both inputs keep `aria-invalid="false"`); (b) the modal has NO distinct X close icon anywhere in its DOM — only "Add section"/"Cancel" — so TC11's "the X icon" dismissal path does not exist as its own control; Escape is used as the only other non-Cancel dismissal and is explicitly flagged as a substitution, not silently treated as equivalent.
5. **AC-12/AC-08/AC-17 cross-session visibility — live, reproducible, only partially diagnosed.** A newly-created Section is not reliably visible in the dropdown immediately after creation (AC-08's auto-select) or on a subsequent same-session, different-perk-type "new session" (AC-12), across repeated live runs — sometimes it appears, sometimes it does not, with no page reload involved in either case. **A "hard-coded backend pagination cap (limit:20)" hypothesis was tested directly against the backend with a standalone script** (`POST /api/v1/web/card/perks/section/list` with no `limit` param, and again with an explicit `limit:100`) — both calls returned **every** Section that existed at the time (documented in this session as ~40+, from repeated automation runs across this PRD), **ruling out** the backend as the bottleneck. The exact client-side (Angular SPA) mechanism was not confirmed — the live browser session used for DOM/network capture became unavailable mid-investigation before the app's own outgoing request could be inspected for this specific case. **This is reported as a genuine, reproducible, live finding — not smoothed over, not fabricated, and not a test-authoring bug** — recommend a follow-up with dev to instrument the actual client-side Section-list refresh logic. The AC-17 regression test's core "no duplication" requirement is unaffected by this (asserted independently as "at most once", which held in every run).
6. **AC-11** requires an actual perk save; gated behind `RUN_PERK_CREATE=1` (off by default) to avoid polluting the perks list on every run, matching the sibling B10-56757 convention. Not executed with the flag set in this session — written and ready, "ATTEMPTED — code path exists, not run this session."
7. **AC-13** — the admin dropdown's own order was recorded (not Breadfast-first in this environment) but NOT asserted against, since both the Figma analysis and requirements-analysis explicitly flag that the admin dropdown's internal order is a separate, unspecified concern from the mobile app's tab order, which this Playwright/web run cannot observe.
8. **AC-14 naming resolution** — the live dropdown data confirms a Section literally named **"General Purchases"** (matching the AC-14 text), not "General" (the stale Figma frame name) — this resolves the Figma-vs-AC discrepancy flagged in requirements-analysis.md Risk 1 in the AC text's favor. The actual perk-to-Section backfill itself (which existing perks show which Section) was NOT queried — that requires DB/API access this Playwright-only run does not have.
9. **Localization sweep** — no dedicated ar-EG portal-locale switcher control was found on the Admin Portal in this session (searched common patterns: language buttons/links, `aria-label*=lang`, class-based switches). The Section dropdown/modal DO already render bilingual EN/AR field content by design (confirmed live, e.g. "Breadfast - بريدفاست"), but a portal-wide locale toggle specifically was not located/exercised — flagged for manual follow-up rather than a fabricated pass.
10. **TC19 upgrade** — rather than the originally-planned "two sequential UI submissions" (a weaker signal), the actual create-section endpoint/payload (`POST /api/v1/web/card/perks/section/create`, `{name_en, name_ar}`) was captured live and reused to fire two **truly parallel** raw API requests (`Promise.all`) with an identical name. Result: exactly one returned 200 and the other 400 "This section already exists" — no server-side duplicate-creation race was found.
